# Agentic RAG with Active Retrieval

A retrieval-augmented generation system that **decides whether to retrieve at all**, reformulates
the query, critiques the retrieved evidence in a bounded retry loop, answers only from approved
chunks with citations, and verifies its own claims against the evidence with an NLI model.

It is measured against two baselines — vanilla single-shot RAG and a closed-book LLM — on three
datasets, with quality, latency and notional cost reported **per dataset, never averaged**.

**The whole system runs at zero cost**: a local Ollama model, the Gemini free tier, a local Qdrant
binary, and local sentence-transformers / DistilBERT / NLI models. No paid API, no billing, no
cloud vector database.

---

## The six blocks

```
            question
               |
      [1] necessity classifier  (DistilBERT, threshold 0.159 on P(retrieve))
               |
        skip --+-- retrieve
         |            |
         |     [2] reformulation agent  (rewrite, or decompose a multi-hop question)
         |            |
         |     +--> retrieval  (Qdrant HNSW, top_k=5)
         |     |      |
         |     |  [3] sufficiency critic  (LLM judge -> sufficient | not_sufficient)
         |     |      |
         |     +--[4] bounded retry loop (max_retries=2, early stop on "no new chunks")
         |            |
         +------> [5] grounded generation  (answer from approved chunks, cite chunk_ids,
                      |                     or say "Insufficient evidence")
                      |
                 [6] answer verification  (split into claims, NLI-check each against contexts)
                      |
                   answer + citations + per-claim support
```

Blocks 1-6 are wired as a LangGraph `StateGraph` in `src/graph/pipeline.py`. The skip path never
touches the vector store.

## Results

**[`docs/REPORT.md`](docs/REPORT.md) is the full write-up**, with figures, every table, and the
caveats discussed in place. It is generated from the results files by
`scripts/make_report_assets.py`, so it cannot drift from the measurements. What follows here is
the summary.

All numbers come from `results/eval/summary.json` (generated by `scripts/run_eval.py`).
"Relaxed accuracy" counts an answer correct on exact match, containment, or token F1 >= 0.8
against the reference.

### Main comparison

| dataset | n | closed-book | vanilla RAG | **agentic (v2)** |
|---|---|---|---|---|
| arXiv (own corpus) | 127 | 0.370 | 0.661 | **0.898** |
| HotpotQA (distractor) | 100 | 0.260 | 0.520 | **0.520** |
| MultiHop-RAG | 100 | 0.190 | 0.400 | **0.420** |

**Read these honestly.** The large arXiv gain is *optimistic*: the generator fix that produced
`agentic_v2` was designed while looking at those questions, so the arXiv column is partly fitted
to its own test set. On the two held-out multi-hop benchmarks the agentic system **ties** vanilla
RAG within the 95% confidence intervals. The agentic system's real, reproducible advantages lie
elsewhere:

| what | vanilla RAG | agentic (v2) |
|---|---|---|
| abstains on MultiHop-RAG *null* questions (answer not in the corpus) | 19% | **88%** |
| unsupported claim rate, arXiv (NLI-checked) | 0.25 | **0.01** |
| RAGAS faithfulness, arXiv | 0.688 | **0.917** |
| false abstention, arXiv | 0.24 | **0.01** |
| mean model seconds per question, arXiv | 0.8 | 8.6 |

So the agentic pipeline buys **groundedness and knowing when to stay silent**, at roughly 10x the
latency. That is the trade-off this project set out to measure.

### Block 1 is the component that actually pays for itself

From `results/ablations/table.md` (103 arXiv questions, one knob changed at a time):

| configuration | relaxed acc | vs full [95% CI] | model s | lite calls |
|---|---|---|---|---|
| **full (agentic_v2)** | **0.903** | (baseline) | 8.6 | 1.30 |
| no_classifier (always retrieve) | 0.699 | **-0.204** [-0.291, -0.117] | 25.3 | 3.61 |
| no_reformulation | 0.922 | +0.019 [-0.019, +0.058] | 4.3 | 0.61 |
| no_critic | 0.893 | -0.010 [-0.029, +0.000] | 4.5 | 0.60 |
| retries_0 | 0.893 | -0.010 [-0.029, +0.000] | 8.2 | 1.20 |
| contexts_3 | 0.913 | +0.010 [-0.019, +0.049] | 6.3 | 1.30 |
| top_k_10 | 0.913 | +0.010 [+0.000, +0.029] | 6.2 | 1.30 |
| int8 collection | 0.903 | +0.000 | 8.6 | 1.30 |

The retrieval-necessity classifier is worth **+20 accuracy points and about 3x less time**; it is
the only ablation whose confidence interval excludes zero. Reformulation, the critic and the retry
loop are each within noise on this question set — stated plainly because that is what the data
says.

### Classifier (block 1)

`results/classifier_metrics.json`: DistilBERT, 1181 train / 148 val / 148 test rows, 49 s on the
GPU. Threshold 0.159 on P(retrieve), chosen on validation to reach 95% retrieve-recall (missing a
needed retrieval is worse than one wasted search).

- test accuracy **0.892** [0.845, 0.939], macro-F1 0.889, retrieve recall **0.918**
- always-retrieve baseline on the same test set: accuracy 0.574, macro-F1 0.365
- held-out **challenge set** (100 rows designed to break the "jargon implies retrieve" shortcut): 0.800
- 88 ms median per query on CPU

### Vector store (section 11)

`results/vector_benchmark.json`: 343,235 chunks, 200 queries, top-k=10, recall measured against
exact search.

| engine | recall@10 | p50 latency | on disk |
|---|---|---|---|
| FAISS flat (exact) | 1.000 | 21.1 ms | — |
| Qdrant HNSW fp32, ef=64 | 0.939 | 2.35 ms | 1101 MB |
| Qdrant HNSW fp32, ef=256 | 0.990 | 3.84 ms | 1101 MB |
| Qdrant HNSW int8, ef=64 | 0.912 | 1.86 ms | 1234 MB |
| Qdrant HNSW int8, ef=256 | 0.958 | 2.53 ms | 1234 MB |

HNSW is about 9x faster than exact search at 94% recall. int8 quantization is a further ~20%
faster at ~3 points less recall, but it **does not save disk here**: Qdrant keeps the quantized
vectors *alongside* the originals, so the int8 collection is larger on disk. Its benefit is RAM
(`always_ram=True` holds the small vectors hot), not storage.

> **Latency caveat.** Every retrieval latency measured before 2026-10-29 was wrong: the
> qdrant-client HTTP transport costs ~28 ms per search on this machine while the server reports
> under 1 ms. `vector_store.prefer_grpc: true` fixed it (search went from ~15 ms to ~1 ms on the
> dev corpus). Do not compare timings across that date.

A clone holds all the code, configuration, figures and measured results, but **not** the data or
model weights: together they are about 5 GB, and single files such as the 527 MB embedding matrix
exceed GitHub's 100 MB limit. Nothing is lost — every excluded artifact is regenerated by a script
in this repo. `.gitignore` names each exclusion next to the command that rebuilds it.

## Setup

Everything below is free. Tested on Windows 11, Python 3.11.9, RTX 3050 (4 GB VRAM), 15.7 GB RAM.

### 1. Python environment

```powershell
python -m venv RAGenv
RAGenv\Scripts\python.exe -m pip install -r requirements.txt
```

`torch` arrives as a sentence-transformers dependency. For GPU training install the CUDA build
explicitly (this project uses 2.14.1+cu126); the CPU build works too, just slower.

### 2. Ollama — the generator (no quota, no key)

Install Ollama, then:

```powershell
ollama pull qwen2.5:3b-instruct
```

It must be running (`http://127.0.0.1:11434`) for any answer generation: closed-book, vanilla RAG
and the agentic pipeline all generate with it.

> **4 GB VRAM warning.** Do **not** run Ollama at the same time as DistilBERT or NLI training.
> Stop it first with `ollama stop qwen2.5:3b-instruct`. The NLI verifier is pinned to CPU
> (`verifier.device: cpu`) for the same reason.

### 3. Gemini free tier — critic, reformulator, judges

Get a free API key from Google AI Studio, **leave billing disabled**, then:

```powershell
Copy-Item .env.example .env
# edit .env and set GOOGLE_API_KEY=...
```

Only `GOOGLE_API_KEY` is read (`src/llm.py`). The other keys in `.env.example` are unused.

Verify every configured model answers:

```powershell
RAGenv\Scripts\python.exe scripts/check_llm.py
```

### 4. Qdrant — the vector store

This project runs the standalone Qdrant binary; no Docker needed. `tools/` is not shipped, so
fetch it yourself: download the Windows release whose version **matches the installed
`qdrant-client`** (1.19.1 here) from Qdrant's GitHub releases and save it as
`tools/qdrant/qdrant.exe`. Docker (`qdrant/qdrant:v1.19.1`) works as an alternative if you map
ports 6333 and 6334.

Start it (storage stays inside the project, in `data/qdrant_storage/`):

```powershell
powershell -File scripts/start_qdrant.ps1
```

> **Always use `127.0.0.1`, never `localhost`.** On this Windows machine `localhost` triggers an
> IPv6 fallback that adds about 2 seconds *per request*. `configs/config.yaml` already does this.

Tests need neither Qdrant nor Ollama nor a key — they use in-memory Qdrant and mocked LLMs.

## Quick start

With Qdrant and Ollama running:

```powershell
# build the dev corpus (500 arXiv papers -> 528 chunks) and index it
RAGenv\Scripts\python.exe scripts/run_ingest.py
RAGenv\Scripts\python.exe scripts/build_index.py

# ask one question through the full agentic pipeline
RAGenv\Scripts\python.exe scripts/run_graph.py --question "How does the Matryoshka hierarchical RAG handle multi-hop questions?"
```

`run_graph.py` prints the whole trace: the classifier's decision, the reformulated or decomposed
query, the retrieved chunks, the critic's verdict for each round, the cited answer, and the NLI
verdict per claim. With no `--question` it runs the demo set from `graph.demo_questions` in the
config.

Useful flags: `--no-classifier` (always retrieve), `--no-verify` (skip block 6),
`--compare-early-stop`, `--compare-multipart`.

### The demo app

```powershell
RAGenv\Scripts\streamlit.exe run app/app.py
```

The same pipeline with the trace laid out visually: the classifier's decision and
confidence, the reformulated or decomposed queries, every retrieved chunk, the critic's
verdict in each retry round, the cited answer, and the NLI check of each claim. Block 1 and
block 6 can be toggled from the sidebar to see what each is doing.

The sidebar checks Qdrant, Ollama and the Gemini key before anything runs and says exactly
what to start if one is missing. If the day's free Gemini quota is exhausted, the app says so
and notes when it resets instead of failing with a stack trace.

## Reproducing the full study

Each step writes to `results/` and resumes where it stopped, so a daily-quota stop is safe.

```powershell
# corpus and index
scripts/run_ingest.py                  # dev corpus; --scale for the 343k-chunk corpus
scripts/build_index.py                 # papers_fp32 + papers_int8
scripts/build_scale_index.py           # scale_fp32 + scale_int8 (needs --scale ingest first)
scripts/build_benchmarks.py            # HotpotQA + MultiHop-RAG, each in its own collection

# block 1
scripts/make_labels.py --estimate-only # print the call budget before spending quota
scripts/make_labels.py                 # retrieve/skip labels by closed-book-vs-RAG experiment
scripts/label_benchmarks.py            # extra labels from benchmark questions
scripts/train_classifier.py            # DistilBERT; stop Ollama first

# blocks 2-6
scripts/run_reformulator.py            # block 2 demo samples
scripts/eval_critic.py                 # block 3 against proxy labels
scripts/run_graph.py                   # the whole pipeline

# baselines and evaluation
scripts/run_baseline.py                # vanilla single-shot RAG
scripts/run_eval.py                    # all datasets x all systems -> results/eval/
scripts/run_ragas.py                   # RAGAS faithfulness / answer relevancy on a sample
scripts/eval_retrieval.py              # retrieval-only metrics

# section 11
scripts/bench_vectors.py               # FAISS vs HNSW fp32 vs int8
scripts/run_ablations.py --estimate-only
scripts/run_ablations.py               # 11 configurations x 103 questions

# section 12
scripts/make_report_assets.py          # figures + docs/REPORT.md from the stored results
scripts/export_papers.py               # papers/papers_used.xlsx: bibliography + both corpora
```

### Quota discipline

The Gemini free tier allows **450 requests per model per day** for the lite models (the config
stops at 90% of the stated limit) and only 20/day for `flash_35`. Three things make large runs
possible:

- **every LLM response is cached** (`data/llm_cache/`), so re-runs are free and identical — the
  entire 11-configuration ablation sweep cost only 214 uncached calls;
- batch scripts catch `DailyLimitReached`, save progress and exit cleanly;
- the daily counter resets at **midnight Pacific**. Local IST is 12.5 h ahead, so work done after
  local midnight still counts against the *previous* Pacific day. Tally a day from
  `results/llm_usage.csv`, counting only rows with `cached=False`.

## Layout

```
src/
  config.py              load_config(); every tunable comes from configs/config.yaml
  llm.py                 call_llm(role=...) — the only way code reaches a provider.
                         Caching, RPM/TPM throttling, daily caps, usage logging, JSON retry.
  ingest/                arXiv fetch, PDF full text, token-accurate chunker
  index/                 embedder, Qdrant store, scale index, FAISS benchmark, hybrid retrieval
  classifier/            block 1: label making, training, calibration, threshold, prediction
  agents/                block 2 reformulator, block 3 critic, and prompts.py (all prompts)
  graph/pipeline.py      blocks 1-6 as a LangGraph StateGraph with the bounded retry loop
  generation/            block 5 grounded generation, block 6 NLI verifier
  eval/                  harness, answer scoring, benchmarks, RAGAS, ablations, report assets
app/                     Streamlit demo: app.py (page) and status.py (service checks)
configs/config.yaml      all tunables: chunk size, top_k, max_retries, models, HNSW, thresholds
data/{raw,processed,labels,benchmarks}/ , data/qdrant_storage/ , data/llm_cache/
data/methods_bibliography.json  the literature and software the method rests on, by block
results/                 metrics, traces, tables, llm_usage.csv
docs/                    REPORT.md and its figures, generated from results/
papers/papers_used.xlsx  methods bibliography + the two arXiv corpora, one sheet each
scripts/                 one entry point per step (see above)
tests/                   308 tests; no server, no key, no model download
```

Model-to-role mapping lives in `llm.roles` in the config and is authoritative:

| role | model |
|---|---|
| generator | Ollama `qwen2.5:3b-instruct` |
| reformulator, critic, label_generation, ragas_judge | `gemini-3.1-flash-lite`, then `gemini-3.5-flash-lite` |
| judge, verifier_fallback | `gemini-3.5-flash` (20 requests/day) |

`llm.model_selection: ordered` means the first model with quota left serves the role, so results
stay reproducible. Never call a provider directly; always go through `call_llm(role=...)`.

## Known limitations

- **The arXiv headline is optimistic.** `agentic_v2`'s generator was tuned while looking at the
  arXiv evaluation questions. Trust the HotpotQA and MultiHop-RAG columns, where it ties vanilla.
- **Reformulation, the critic and the retry loop are not individually proven.** Every ablation
  except `no_classifier` sits inside the noise on 103 questions. More questions would be needed
  to resolve effects that small.
- **Hybrid retrieval (dense + BM25 + reranker) exists but is unused.** `src/index/hybrid.py` is
  implemented and benchmarked; it did not improve answers (HotpotQA 0.49 / 0.53 vs 0.52 dense), so
  the graph stays dense-only.
- **The 343k-chunk scale corpus is only used for the vector benchmark.** The pipeline and all
  quality evaluation run on the 528-chunk dev corpus, so retrieval quality is not measured at
  scale.
- **A 3B generator is the ceiling on answer quality.** Several errors are generation failures on
  correctly retrieved evidence, not retrieval failures.
- **`flash_25` (gemini-2.5-flash) is unavailable** (HTTP 404, "no longer available to new users").
  No replacement has been chosen, so `judge` and `verifier_fallback` have only `flash_35` with its
  20 requests/day. RAGAS uses the lite models instead.
- **Benchmark classifier labels are noisy and few** (HotpotQA 10 rows at 0.50 accuracy,
  MultiHop-RAG 11 at 0.36); the classifier is only really validated on arXiv-style questions.
- **Costs are notional.** Actual spend is $0. The `notional_usd_per_1m_*` fields are unset, so the
  cost columns are blank; fill them in the config to get a paid-tier equivalent.
